
## 7. No arbitrary acceptance threshold for first integration attribution run

The first end-to-end integration run is deliberately an **attribution run**, not a certification gate.

Reason:

- S and P estimators are accepted;
- D semantics are frozen but D estimator v3 is already known not to be certified;
- assigning a new overall accuracy threshold now would mix a known component limitation with a new arbitrary system-level pass/fail rule.

Therefore the first fresh integrated run pre-registers the metrics and error taxonomy but **does not invent a post-hoc global acceptance threshold**.

Layer A wiring still has an exact requirement: 8/8.

After the first Layer B result, decide whether:

```text
A. integration is clean and D residuals are tolerable for dogfooding;
B. D causes repeated operational false DROP / false AWARE and needs implementation work;
C. a new cross-component semantic interaction exists;
D. sensor/evidence plumbing is the limiting factor.
```

Only then should a product-level acceptance gate be set.

## 8. Failure taxonomy

Classify every residual before changing anything:

```text
D semantic-definition failure
D clause-application / extraction failure
S semantic-definition failure
S estimator application failure
P semantic-definition failure
P evidence interpretation failure
P insufficient-evidence behavior
Evidence Packet / sensor failure
cross-component case inconsistency
Boolean composition / scheduler wiring failure
Human policy boundary / noisy Gold
technical / provenance failure
```

A final action may be correct even when one component is wrong if the Boolean gate masks the error. Such cases must still be recorded as **masked component errors**, not counted as fully correct component behavior.

Likewise, an incorrect component only matters operationally when it changes the final Boolean outcome; record **causal final errors** separately from masked residuals.
