# 2. Proposed minimal sufficient semantic basis

## U01 — How torch.profiler is used and what its two output views mean

The tutorial's profiling method is: prepare the workload, optionally annotate it with `record_function`, profile CPU/CUDA activity with `torch.profiler.profile`, advance profiling steps, and export both a statistics table and a time-resolved trace. The table answers aggregate questions such as what consumes time and how often events occur; the trace answers when/why operations occur across CPU/GPU timelines. `Self` time excludes child events while `total` time includes them.

Evidence anchors:

```text
PARA 0020–0026
PARA 0033
```

Why one unit:

> These details jointly define one method: how to collect and interpret the two complementary profiler views.

## U02 — Workload size determines whether the program is overhead-bound or compute-bound

For 64×64 BF16 matmul+add, CPU-side launch/scheduling overhead dominates while GPU work is tiny (`2.314 ms` Self CPU vs `23.104 µs` Self CUDA), making the workload overhead-bound. Increasing the matrix to 4096×4096 raises useful GPU work (`4.908 ms` Self CPU vs `4.495 ms` Self CUDA) and shifts the workload to a compute-bound regime.

Evidence anchors:

```text
PARA 0040–0041
```

Why one unit:

## U03 — Cold-start costs should be separated from steady-state measurement rather than mistaken for recurring work

The abnormally long first measured step is attributed to one-time initialization such as workspace allocation, cuBLAS heuristic setup, or lazy loading. Warmup iterations and profiler scheduling move these one-time effects outside the active measurement window; warmup does not optimize them away, it prevents them from contaminating steady-state measurements.

Evidence anchors:

```text
PARA 0048–0053
PARA 0057
```

## U04 — Profiler instrumentation can itself create trace gaps, so repeated observation is needed to distinguish tool artifacts from application behavior

The apparent ~2.5 ms CPU/GPU offset and an intermittent gap between GPU kernels are traced to `Activity Buffer Request` / profiler buffer allocation behavior. Extending active sampling shows the gap occurs only once, supporting the conclusion that it is profiler instrumentation rather than recurring business-code latency.

Evidence anchors:


## U05 — PyTorch execution can be read as a layered dispatch chain, and tensor shape changes the selected backend operation

The trace exposes a nested path from `ProfileStep` to the custom `matmul_add` marker, then `aten::matmul`, then the backend operator. Two-dimensional matmul dispatches to `aten::mm`; adding a batch dimension changes dispatch to `aten::bmm`, with additional runtime work for backend selection.

Evidence anchors:

```text
PARA 0065–0067
PARA 0071
```

---

## U06 — Occupancy queries are a diagnostic signature of resource-heavy adaptive kernels

`aten::mm` triggers `cudaOccupancyMaxActiveBlocksPerMultiprocessor` before `cudaLaunchKernel`, whereas lightweight elementwise add does not. cuBLAS uses occupancy/resource information as part of heuristic kernel selection for heavy GEMM-like kernels; lightweight fixed-resource kernels can launch directly. The presence or absence of this query is therefore a useful trace-reading clue.

Evidence anchors:

```text
PARA 0073–0078
```

---

## U07 — A long cudaDeviceSynchronize at the end of a profiling window is principally synchronization/profiler-flush time, not CPU computation

`cudaDeviceSynchronize` blocks the CPU until GPU work completes so profiler events can be flushed. In the small-workload example, ~26 µs of useful GPU work paired with ~1.78 ms synchronization indicates extreme idle/overhead dominance; the synchronization duration should not be misread as ordinary CPU compute time.

Evidence anchors:

```text
PARA 0080–0081
```

---

## U08 — Identical GPU kernels have variable runtime, so aggregate averages can hide the causal performance picture

Repeated 4096×4096 runs of the same kernel vary because of clock state, temperature, power scheduling, and driver/background effects. A mean near 1084 µs can conceal that most runs are around 580 µs with a smaller number of slow disturbances; therefore trace distributions/outliers can lead to different optimization conclusions than a simple average.

Evidence anchors:

```text
PARA 0085–0091
```

---

## U09 — torch.compile has both a compile-time pipeline and persistent runtime machinery

The source describes the compilation path as TorchDynamo capturing Python into an FX graph, AOTAutograd constructing forward/backward graphs when gradients are involved, and Inductor lowering the graph into optimized CPU/GPU code. At runtime, compiled execution still includes cache lookup / guards, AOTDispatcher wrapper work, and execution of a cached `CompiledFxGraph`; these wrappers remain part of each invocation rather than disappearing after compilation.

Evidence anchors:

```text
PARA 0093
section: “torch.compile 的运行时架构”
```

---

## U10 — torch.compile's observed optimization is operator-level fusion, not necessarily one fused GPU kernel, and small workloads can pay extra runtime overhead

For this matmul+add example, Inductor rewrites separate `aten::mm` + `aten::add` into `aten::addmm`, but the GPU still uses the same cuBLAS GEMM. Bias handling requires a DtoD copy to initialize the output buffer before GEMM epilogue processing, so the result is not a single zero-extra-memory fused CUDA kernel. The compiled version also has roughly higher per-call CPU overhead in this tiny workload because Dynamo/AOTAutograd/Inductor runtime machinery has a fixed cost that large multi-operator graphs can amortize better.

Evidence anchors:

```text
PARA 0100
PARA 0112
section: “CPU 开销不降反升”
```
